{% endmacro %} {% set code = "block bg-slate-900 text-slate-100 rounded px-3 py-2 text-xs font-mono overflow-x-auto whitespace-pre" %} {% call card("What this is") %}

A verification server. Field devices photograph a board, run a small model, and upload here. This box runs the heavy model on the upload and stores both predictions so you can check how the small model is doing.

It is model-agnostic: the class names, input size, and preprocessing all come from inside each model archive — nothing about a specific model is baked into this server or these pages.

{% endcall %} {% call card("1 · Register a model") %}

Go to Models → Register an archive. Upload a TorchScript .ts.pt or an ONNX .onnx file. Give it an id and version, tick Activate to make it the live model for its task.

Task, classes, and preprocessing are read from metadata inside the file — nothing to configure.

ONNX note: torch.onnx.export embeds no metadata, so paste the manifest into the Metadata JSON field when registering. It's stored with the model. An embedded manifest, if the file has one, always wins.

{ "classes": ["a", "b", "c"], "task": "classification", "image_size": 224, "max_views": 1, "normalize_mean": [0.485, 0.456, 0.406], "normalize_std": [0.229, 0.224, 0.225] } {% endcall %} {% call card("2 · Load vs. Activate") %}

Activate = the model new uploads are graded against (one per task).

Load = pull it into GPU memory now so the first prediction isn't slow. Only one model fits in memory at a time; loading another unloads the first.

{% endcall %} {% call card("3 · Make an API key") %}

On API keys:

  • ingest key — for a field device. Bound to a device id; its uploads are attributed to that device. This is what goes in the phone/camera client.
  • admin key — logs into this UI and manages models and keys.

The key is shown once, right after you create it. Copy it then.

{% endcall %} {% call card("4 · Upload a board (what your client codes against)") %}

Multipart POST. 1–3 views, one lighting label each, optional edge prediction and metadata. Idempotent on board id + image bytes, so retries never duplicate.

curl -X POST http://THIS-HOST:8000/v1/boards \ -H "X-API-Key: YOUR_INGEST_KEY" \ -F "board_id=board-0001" \ -F "task=classification" \ -F "views=@both.png" -F "lighting=both" \ -F "views=@light_a.png" -F "lighting=light_a" \ -F "views=@light_b.png" -F "lighting=light_b"

Full contract with every field: API docs.

{% endcall %} {% call card("Running the server (on the Jetson)") %} cd ~/JetsonAPI git pull origin main sudo ./setup-jetson.sh deploy # build, start, show access panel sudo ./setup-jetson.sh access # reprint IPs, URLs, admin key, login QR

Reach it remotely over Tailscale — both the Jetson and your device must be on the same tailnet. The access panel prints a QR: scan it to log in without typing.

{% endcall %} {% call card("When something's off") %}
  • Uploads work but no server prediction → no active model for that task. Activate one under Models. Check Dashboard → Recent errors.
  • Logs: docker compose logs -f gateway
  • Health: /health
