What this is

A verification server. Devices in the field photograph a sample, run a small model on the spot, and upload here. This machine runs the big model on that upload and keeps both answers, so you can measure how well the small one is doing.

It is model-agnostic: class names, input size and preprocessing all come from inside the model file. Nothing about any particular model is built into this server or these pages.

Models

Two file types work: TorchScript .ts.pt and ONNX .onnx.

Activate vs. Load — they're different

Activate Makes it the model new uploads are graded against. One per task type.
Load Pulls it into GPU memory now, so the first prediction isn't slow. Only one model fits at a time — loading another evicts it.
ACTIVATE — which model answers

One active model per task type.

LOAD — what is in GPU memory

Optional — saves the first-call delay.

You don't have to Load manually. The server loads on demand; this just avoids the one-off cold start.

ONNX files need their manifest

TorchScript exports carry their settings inside the file. torch.onnx.export does not — so for a plain ONNX export, paste this into the Metadata JSON box when registering:

{ "classes": ["a", "b", "c"], "task": "classification", "image_size": 224, "max_views": 1, "normalize_mean": [0.485, 0.456, 0.406], "normalize_std": [0.229, 0.224, 0.225] }

classes must be in the same order your training used. image_size and the normalize values must match your eval transform — a mismatch won't error, it will just make every prediction wrong.

API keys

Every request needs one. Create them on the API keys page.

ingest

For a field device. Tied to one device id, so uploads are attributed to it and a misbehaving client can't claim to be another. Upload only.

admin

Logs into this UI, manages models and keys. Give each person their own so you can revoke one without disturbing the others.

A key is shown once, right after you create it. Copy it then — only a hash is stored, so it can never be recovered, only replaced.

For client developers

Full interactive reference at /docs.

Just get a prediction

Answer comes straight back. Nothing stored.

curl -X POST http://THIS-HOST:8000/v1/predict \ -H "X-API-Key: YOUR_KEY" \ -F "images=@photo.jpg"

Upload a capture to keep

Stores the images, runs the active model in the background, records both predictions. Safe to retry — re-sending the same capture never duplicates it.

curl -X POST http://THIS-HOST:8000/v1/boards \ -H "X-API-Key: YOUR_INGEST_KEY" \ -F "board_id=sample-0001" \ -F "task=classification" \ -F "views=@front.png" -F "lighting=both" \ -F "views=@side.png" -F "lighting=light_a"

One lighting label per image, same order. 1–3 images; sending fewer is normal, not an error.

Running the server

On the Jetson itself.

cd ~/Desktop/JetsonAPI git pull origin main sudo ./setup-jetson.sh deploy # rebuild and restart sudo ./setup-jetson.sh access # print URLs, admin key, login QR

The stack restarts by itself after a reboot or power cut. To stop it on purpose use sudo systemctl stop jetsonapi.

Access is over Tailscale only — nothing is exposed to the internet. To let someone else in, share the machine from the Tailscale admin console and give them their own admin key.
